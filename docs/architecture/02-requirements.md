# 02 — Architecture Requirements

Every requirement carries a **classification** and a **source**:

- **Confirmed**: supported by current code, the README, CI configuration, existing design documents, or an explicit project constraint for this redesign.
- **Proposed**: introduced by this architecture. It needs team agreement and, for numbers, measurement.
- **Assumption**: believed true but not verified. It is listed so it can be challenged.

Requirement IDs are referenced from [03](03-target-architecture.md), [04](04-grading-workflow.md), [06](06-security.md) and [07](07-migration-plan.md).

## 3. Performance and scalability

No performance baseline exists. The values below are **proposals that need measurement** in phase P4 of the [migration plan](07-migration-plan.md). They must not be treated as commitments until they have been measured on Windows, macOS, and Linux.

| ID     | Requirement                                                                                                                                                                                                                          | Class                |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------- |
| PERF-1 | Measure and record per platform: (a) the overhead of starting a container (create → start → exit for a trivial binary), (b) compile time for a typical 1–5 file submission, (c) throughput of a batch against concurrency (1, 2, 4). | Proposed             |
| PERF-2 | Batch concurrency is bounded and configurable. The default is chosen from PERF-1 data (**open decision D1**); the starting proposal is 2.                                                                                            | Proposed             |
| PERF-3 | The image pull happens before any timed step and never counts against a compile or test timeout.                                                                                                                                     | Proposed (fixes W10) |
| PERF-4 | Progress events to the UI are throttled (proposal: at most one per run every 250 ms, plus every state change).                                                                                                                       | Proposed             |
| PERF-5 | Captured output is bounded in memory. The proposed capture limit is 1 MiB per stream, with 64 KiB stored inline in SQLite.                                                                                                           | Proposed             |
| PERF-6 | Assumption: a single instructor batch is at most a few hundred submissions × tens of test cases. Nothing in the design requires a distributed queue at that scale.                                                                   | Assumption           |

## 4. Reliability

| ID    | Requirement                                                                                                                                                         | Class                                                |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| REL-1 | A failure of the infrastructure (Docker unavailable, image missing, container fails to start, disk I/O error) must **never** be recorded as a student's grade.      | Proposed (fixes W13)                                 |
| REL-2 | Every container and temporary workspace a run creates is removed when the run ends, whether it succeeds, fails, or is cancelled.                                    | Proposed (fixes W9, W11)                             |
| REL-3 | After a crash or forced quit, the next start marks interrupted runs as failed and removes containers and workspaces left behind.                                    | Proposed                                             |
| REL-4 | Grading one submission is independent of the others: one failed run does not fail the batch.                                                                        | Confirmed (historical loop continued after failures) |
| REL-5 | Results are written as each run progresses, so completed runs survive a crash in the middle of a batch.                                                             | Proposed                                             |
| REL-6 | Student code is never retried automatically. Only infrastructure operations that are known to be transient (container creation or start) are retried, at most once. | Proposed                                             |
| REL-7 | Grading is reproducible: each run records the submission hash, the test suite hash, the grading policy, and the compiler image reference.                           | Proposed                                             |

## 5. Security

The full threat model is in [06](06-security.md).

| ID    | Requirement                                                                                                                                                                                                         | Class                                                   |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| SEC-1 | Treat all submitted source code, and the binaries built from it, as untrusted.                                                                                                                                      | Confirmed (project constraint)                          |
| SEC-2 | Untrusted code runs only inside containers that have no network, all capabilities dropped, `no-new-privileges`, memory, CPU and process limits, a read-only root filesystem, and a non-root user on every platform. | Confirmed (first four, current flags) / Proposed (rest) |
| SEC-3 | Only per-run workspace directories created by the engine are mounted into containers, never directories the user selected.                                                                                          | Proposed (fixes W3)                                     |
| SEC-4 | Disk writes and captured output from containers are bounded.                                                                                                                                                        | Proposed (fixes W4, W5)                                 |
| SEC-5 | The renderer never supplies a host path that the engine mounts or executes. File selections are referenced by opaque IDs issued by the main process.                                                                | Proposed (fixes W1)                                     |
| SEC-6 | Filesystem paths derived from user input are built only from engine-generated IDs or sanitised segments, and must stay inside their root directory.                                                                 | Proposed (fixes W7)                                     |
| SEC-7 | Symbolic links in submissions are rejected.                                                                                                                                                                         | Proposed                                                |
| SEC-8 | IPC inputs to grading channels are validated in the main process before use.                                                                                                                                        | Proposed                                                |
